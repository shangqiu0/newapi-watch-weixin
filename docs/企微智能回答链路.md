# 企业微信智能回答链路修正说明

## 用户澄清的重点
大模型必须改善企业微信群聊/私聊中返回给用户的回答，不是仅在Web页面上增加一个聊天框。回答需要先取当前平台的真实数据，再给出自然、简洁、有结论的说明，而不是对未知自然语言返回命令帮助清单。

## 已修正的实现

- 原来的`serve`入口也把`Runtime.bot`接入`Assistant`；不再只在多平台Console里接模型。
- 启用模型后，`渠道状态`、`统计`等短查询同样走模型+工具，除明确本地运维变更命令外不绕过模型直接贴模板。
- 模型首轮要求tool调用，服务端同时检查本次是否成功取得对应数据；没有实际数据工具证据的运营状态/数值不会直接发送到企微。
- 能力说明工具不能充当渠道/消耗状态的证据。所有工具仅服务机器人绑定平台，参数中夹带其他platform_id/SQL/渠道变更会被拒绝。
- 工具返回结构化摘要、采集时间、数据新鲜度/覆盖范围与统计口径，而不是整块旧帮助模板。
- 回复策略：先说结论、再用少量数据解释，必要时说下一步；默认简短，只有用户明确要求才展开。手动禁用不冒充故障，没有错误正文不能断言原因，quota不能擅自转货币。
- 企微先发送同条流式“正在查询”，最终答案更新同一个stream_id。重复消息回调不会多发最终答案。
- 模型失败时，只基于当前本地快照给短说明；明确快照时间和限制，不编造“全部正常”或消耗金额。

## 原单平台serve如何启用

真实.env当前还没有模型配置字段；本轮没有替用户修改.env，也没有借用管理令牌调用模型。

在本地.env补充（值按自己的模型服务填写，勿把真实Key贴到对话中）：

```dotenv
WATCH_LLM_ENABLED=true
WATCH_LLM_BASE_URL=https://你的兼容模型服务/v1
WATCH_LLM_API_KEY=独立的模型调用Key
WATCH_LLM_MODEL=支持工具调用的模型ID
WATCH_PLATFORM_NAME=你的平台名称
```

如果用现有NewAPI转发模型，BASE_URL填该NewAPI的`/v1`地址；API_KEY应使用模型调用令牌，不是`WATCH_NEWAPI_TOKEN`管理访问令牌。模型必须支持Chat Completions function tools。字段不完整会拒绝启动，不能只把开关设为true。

只重启本监控服务后生效，不重启NewAPI。启动后在企微群内@机器人或私聊发送自然问题，例如“现在有哪些渠道需要注意？”“今天用量比昨天多在哪里？”“帮我画近7天的模型消耗排行”。多日数据未采集齐时应如实说明。

多平台Console中的每个bot同样绑定自己的Assistant和模型配置；Web智能问答只是方便管理者验证同一链路，不是替代企微回答。

## 验证与尚未完成的边界

`tests/test_wecom_ai_v03.py`使用真实SDK回复构造，仅替换外部HTTP模型和企微传输。覆盖群/私聊消息进入原Runtime、实际SQLite渠道取数、两轮模型工具调用、自然中文最终回复、同条流式和去重、无证据拒绝、故障降级、配置缺失。

这证明程序主链路已接通，不代表已经接通用户真实模型。真实模型Key和model尚未填入.env，尚未做付费模型调用或真实企微问答验收。本轮不会声称“真实企微已在用大模型”。
