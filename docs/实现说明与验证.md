# 实现说明、审查与验证

日期：2026-11-10。实现版本：0.1.0。

## 1. 用户确认的最终边界

- 外部独立服务；不修改、不重启 NewAPI。
- 所有企微参与者权限一致；没有注册、登录、RBAC、账号绑定或多租户。
- 统一 HTTP 服务密钥、事件验签、敏感字段白名单仍保留，它们不是用户权限分层。
- 本版是独立运维工具，不是通用聊天平台，也不依赖 LLM/MCP 才能监控。

## 2. 二开决策与代码来源

已审阅 `li0on3/newapi-monitor` 的 README、requirements 和主要单体实现（约2500行），以及 NewAPI 官方渠道/用户/日志/通知源码和企微SDK。

最终没有整仓 fork，也没有复制上游实现：不引入多用户后台/SSO和无关依赖，采用当前目录内独立模块化实现。参考的是外部监控、告警outbox等架构思路；NewAPI和WeCom作为API/SDK依赖，不修改其源码。

本次使用的技能：writing-plans、executing-plans、python-dev、backend-engineering、api-design、db-design、test-driven-development、test-engineering、systematic-debugging、code-audit、requesting-code-review、verification-before-completion。仓库未初始化Git，没有创建分支/提交；未获子代理授权，未派遣代理。

## 4. 测试与审查方法

- 测试先失败后实现；后续发现的问题通过失败回归测试定位再修复。
- 真实SQLite、真实httpx客户端、真实SDK回复构造；仅替换远端传输。
- 一个测试实际启动独立Python进程和TCP监听，验证HTTP鉴权、渠道、用户查询和PNG下载，结束后清理该进程树。
- 对比计划做作者自审，不声称已经由独立审阅者审查。

### 已发现并修复的可靠性问题

1. 清理日志后覆盖起点未更新，旧日报可能误标完整 → 覆盖起点随保留期推进。
2. 通知限速原本仅内存维护，重启会绕过 → 最近发送尝试时间持久化。
3. 错误窗口记录不足被当成恢复 → 样本不足不做恢复判定。
4. HTTP主动测试/静默缺少请求去重 → 统一幂等键，重复409，命令并发/超时控制。
5. 机器人处理前长时间去重可能在进程崩溃后丢查询 → 短处理租约，回复成功后延长，失败释放。
6. 同渠道并发测试可能重复消耗额度 → 单渠道锁与持久化最近探测缓存。
7. Windows管道中文使用旧代码页 → CLI非交互输出显式UTF-8，独立进程回归测试。
8. 日报启动时与首次日志采集竞争 → 首次日志采集成功后才允许定时日报。
9. 开发依赖pytest旧版本审计发现已知漏洞 → 升级修复版本9.0.3，更新锁文件并全量复测。

## 5. 安全自审

- 所有HTTP运维数据端点使用同一个服务密钥，无角色区别；密钥使用常量时间比较。
- 外部事件用原始报文HMAC、签名内时间戳、防重放和64KiB报文限制。
- 不接受群聊中的任意URL、SQL、Shell或Python代码；插件只能由部署者安装并显式启用。
- SQL参数化；不把外部HTTP放入SQLite事务。
- 数据库和回复不保存渠道key、用户密码、完整错误正文、原始SDK帧。
- 异常返回安全消息和错误ID；HTTP客户端和SDK敏感调试输出受限。
- 主动探测默认关闭；不提供自动启用/禁用/删除渠道。
- NewAPI凭证不跟随重定向；生产建议HTTPS，明文HTTP仅限受信私网。

## 6. 未实测的边界 / 延后项

- **真实NewAPI只读接口、企微群Webhook服务端接收、企微长连接认证现已通过，详见第9节。** 群@/私聊触发查询及图片显示尚未端到端验收。
- **Docker生产镜像已实际构建并验收。** 已验证非root、只读根文件系统、独立数据卷、HTTP鉴权、查询/PNG、重启持久化和Docker健康检查；Compose配置解析通过，未使用真实凭证启动生产Compose服务。
- CI配置已生成，尚未在远端GitHub Actions执行。本地Windows/Python3.13.5与Linux容器/Python3.13.18的全量测试均通过；Python3.12矩阵未在本机运行。
- 官方企微SDK引用websockets旧接口，测试有2条第三方弃用警告，当前不影响测试；未修改/屏蔽第三方代码。属于延后的Minor兼容性观察项。
- 不做任意自然语言Agent、MCP、通用Web面板、多实例界面、语音解析、自动修复、插件热加载、企微自建应用私推、死信聊天重放。
- 单进程单实例。至少一次通知可能重复；同一队列的旧消息退避会延迟后续消息；没有无限重试或“绝对秒级”承诺。

## 7. 真实平台联调清单

1. 先配置独立数据库、NewAPI管理访问令牌和用户ID，运行 `newapi-watch check` / `once`。
2. 对照后台核对渠道总数，确保已禁用渠道也在列表，核对日志时间窗口和quota。
3. 在测试渠道验证自动禁用/恢复；手动禁用单独验收，不用它冒充自动禁用。
4. 配群通知Webhook，发送一次测试异常并确认企微实际收到了告警与恢复。
5. 配智能机器人长连接，分别在群 @ 和私聊查询渠道、用户；确认不同发送者功能一致。
6. 在群/私聊验证日报图片显示、消息长度、忙碌/断线恢复、机器人安装范围。
7. 可选配置NewAPI事件地址与secret，验证验签和网络可达性；不需要事件时保持关闭。
8. 上线前验证Docker和备份；升级只重启本服务，不操作NewAPI容器。

### 容器验证过程中发现并修复

- `tests/verify_container.ps1`：临时宿主端口在Docker重启后可能变化，原脚本继续访问旧端口导致超时。已通过独立前后端口对比定位，并在重启后重新读取实际绑定。修复后运行验收通过，生产Compose使用固定端口不受此问题影响。
- `Dockerfile:6`：原`setuptools==80.9.0`在实际镜像依赖审计中出现已知漏洞记录。已按修复版本升级到`84.1.0`，重建镜像，重新执行容器验收、Linux全量测试和依赖审计。旧审计结果保留在`artifacts/container-pip-audit-before-fix.json`。
- `tests/Dockerfile.validation.dockerignore`：验证镜像使用专用构建上下文过滤规则，只包含测试与pyproject，不将本地.env或数据库带入镜像。

### 复现容器验收

```powershell
docker build -t newapi-watch:local .
pwsh -File tests/verify_container.ps1
docker build -f tests/Dockerfile.validation -t newapi-watch:validation .
docker run --rm --network none newapi-watch:validation
```

验收脚本使用随机名称和独立数据卷，结束后清理本次临时容器及卷。保留两个本地镜像供继续验证，不启动常驻生产服务。镜像依赖审计只表示对应Python漏洞源的查询结果，不等同于整张OS镜像的全面漏洞扫描。
